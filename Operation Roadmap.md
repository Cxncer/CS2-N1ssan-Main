# 1. Project vision

N1SSAN is a CS2 inventory and loadout customization system.

The objective is to let users manage their CS2 inventory and loadouts through a custom desktop application and web interface, with a native DLL responsible for applying the selected configuration inside CS2.

The intended experience:

# CS2 LORE

N1SSAN ECOSYSTEM

WELCOME

Application entry point

DOMINATE

Startup orchestration · Game detection · Runtime monitoring

LOADOUT

Manage and apply CS2 loadouts

ARMORY

Inventory management and customization

N1SSAN NATIVE RUNTIME

n1ssan-dll.dll · Native CS2 integration

Critical architectural decision: There is no separate N1SSAN screen after DOMINATE. DOMINATE is the orchestration layer. LOADOUT and ARMORY are destinations within the same application experience.

The native DLL should own both Loadout and Inventory/Armory runtime logic.

## 3. New repository — n1ssan-injectorv2

New canonical injector

[Cxncer/n1ssan-injectorv2](https://github.com/Cxncer/n1ssan-injectorv2?utm_source=chatgpt.com)

This is an important architectural change. The injector is now a standalone application rather than an experimental collection of injection stages.

### Verified implementation

| Component                | Responsibility                             |
| ------------------------ | ------------------------------------------ |
| `Program.cs`             | Main application and injection workflow    |
| `DllInjector.cs`         | Native DLL injection                       |
| `DllInspector.cs`        | PE architecture and dependency validation  |
| `GameProcess.cs`         | CS2 process detection and readiness        |
| `InjectorConfig.cs`      | DLL discovery and MinHook validation       |
| `DllStatusWatcher.cs`    | Native DLL heartbeat and status monitoring |
| `NativeMethods.cs`       | Windows API declarations                   |
| `app.manifest`           | Application execution permissions          |
| `n1ssan-injector.csproj` | .NET 8 x64 configuration                   |

Repository's only commit currently: Initial Commit. Branch: main.

### Injection workflow

1. Find n1ssan-dll.dll

   Resolve the DLL path through arguments, environment variables, or project discovery.

2. Validate dependencies

   Check x64 PE architecture, imported functions, dependencies and MinHook.

3. Find CS2

   Locate `cs2.exe` and select the appropriate process.

4. Wait for game readiness

   Wait for `client.dll` and allow a three-second settling period.

5. Inject

   Use Windows process APIs and a remote x64 loading stub.

6. Verify injection

   Confirm the DLL is present in the game's module list.

7. Wait for native readiness

   Read the DLL status heartbeat until READY, DEGRADED, FAILED or timeout.

### Status protocol

The injector expects the DLL to publish:

```
%LOCALAPPDATA%\n1ssan\status\
    cs2-<pid>.status
```

Protocol:

```
N1SSAN_STATUS|1|<UTC timestamp>|<pid>|
<build id>|<state>|reason=<reason>
```

Supported states:

| State         | Meaning                                                     |
| ------------- | ----------------------------------------------------------- |
| INITIALIZING  | DLL starting                                                |
| CHECKS_PASSED | Preflight checks passed                                     |
| READY         | Runtime initialized                                         |
| DEGRADED      | Runtime initialized with optional functionality unavailable |
| FAILED        | Initialization failed                                       |

The heartbeat must be fresh (30 seconds or less).

The injector also supports:

- `--dll`
- `--pid`
- `--wait`
- `--no-wait`
- `--inject-timeout`
- `--status-timeout`
- `--no-status`
- `--no-deps`
- `--skip-client-wait`
- `--elevate`
- `--quiet`
- `--version`

It uses machine-readable exit codes and a final `RESULT=OK` or `RESULT=FAIL` line.

### Important implementation details

- Does not modify CS2 game files.
- Does not modify Steam.
- Does not unload the DLL.
- Does not free remote memory while the remote thread might still be executing.
- Requires CS2 to run with `-allow_third_party_software`.
- Requires the x64 Release DLL and its MinHook companion.

### B. Armory

Armory evolved into a structured inventory management system.

The web bridge now has a formal Armory document contract.

The data structure includes:

```
ArmoryDocument
 ├── schemaVersion
 ├── catalogueVersion
 └── profiles[]
      ├── profileId
      ├── name
      ├── items[]
      │    ├── instanceId
      │    ├── definitionId
      │    ├── type
      │    ├── quality
      │    ├── rarity
      │    ├── finish
      │    ├── statTrak
      │    ├── stickers
      │    ├── charm
      │    └── metadata
      └── equipment[]
```

The validator checks item types, wear values, sticker slots, equipment compatibility and document-wide instance identity uniqueness.

This contract is important. Future changes must preserve compatibility between the web bridge and native DLL.

### C. DOMINATE


There is also a failure state.

The launcher currently has:

- Bridge process management.
- Vite web application management.

- Startup state transitions.

The critical outstanding issue is that its source code still explicitly says DLL integration is not implemented in the startup pipeline.
